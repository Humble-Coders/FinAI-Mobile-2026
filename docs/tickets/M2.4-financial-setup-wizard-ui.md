# [M2] Build the financial setup wizard

## 📖 Story / Why

Right after signup, users get a short wizard: monthly after-tax income and monthly expense — **both mandatory** — then existing debts and loans, current investments (amounts only in v1), and basic monthly obligations, all **optional** (PRD F1, §9). Its answers seed the first dashboard (M4), so a new user sees something meaningful before they upload a single statement.

Two things make it more than a form. It is **money input**, so every figure is a decimal string end to end through a shared `Money` utility — never `Double`, never cents in client code (`CLAUDE.md` → Money). And it must not feel like a wall: two figures are the whole price of entry, every later step is skippable, and the wizard is resumable if the app is closed.

## 🧭 Context

- Repo: `FinAI-Mobile-2026`. Android (Compose) and iOS (SwiftUI) native UI over `sharedLogic` (`kmp-arch-v2`).
- **No brief.** M2 is drafted from `docs/ROADMAP.md` (2.4) and the PRD, which are the yardstick for review (manager decision, 2026-09-11).
- **Part of this wizard is mandatory** (manager decision, 2026-09-12 — PRD §9; ticket 2.5, Humble-Coders/Finance-backend#29): **income and monthly expense cannot be skipped**, and the app cannot reach home until both are saved — the API reports `financial_setup` in `onboarding_required` until then. Debts, investments and the itemised obligations stay **optional**, keep their Skip, and are editable later from the profile. 2.5 adds the `monthly_expense` field and the gate; this ticket builds the screens against it.
- **The API is 2.2 as amended by 2.5:** `GET /financial-setup` and `PUT /financial-setup` (full replace, idempotent — call it after every step, and **send the whole wizard every time**: omitting `income` clears it and re-raises the gate). The payload carries `income` and `monthly_expense`; there is **no `status` field and no skip endpoint** (PRD §9, 2026-09-12). Amounts travel as decimal strings; the server converts to minor units.
- **There is no `Money` utility in `sharedLogic` yet**, although `CLAUDE.md` requires one for every amount. This ticket creates `sharedLogic/.../util/Money.kt`: parse and normalise user input, compare, format for display using the capabilities `locale` and `currency` — decimal-string arithmetic only, blank or unparseable input reads as `"0"`, never a crash (`kmp-arch-v2` → Money).
- The currency and locale come from the capabilities payload (`KtorCapabilitiesRepository`, #6) — never hardcoded, never branched on country.
- Navigation and the signed-in/onboarding router arrive in **2.3**; this ticket adds the wizard as the step after onboarding and before home.
- Shared HTTP client, typed `ApiException`, `@Throws` guard and strings registry all exist from #6.

- **Design: the PM provides the approved design; it is not attached to this issue.** At `/start-ticket`, ask the PM for it before building. The bar is to **match it exactly** — spacing, sizing, colour, type and every state — not to approximate or improve it (manager decision, 2026-09-11).

## ✅ Scope / What to build

- [ ] **`util/Money`** in `sharedLogic` with `commonTest` coverage: normalise (`"1,200"`, `" 1200.5 "` → `"1200.50"`), reject what cannot be money, compare, format with locale and currency. No `Double` anywhere.
- [ ] **Models + repository** in `sharedLogic`: `FinancialSetup` (income, monthlyExpense, debts, investments, obligations) with defaults on every field; `FinancialSetupRepository` + `KtorFinancialSetupRepository` (`get`, `save`) with `@Throws(ApiException::class, CancellationException::class)`.
- [ ] **Wizard state in shared**: one blocking-reason function per step (e.g. an amount that is not money, an empty debt name), read by the disabled Continue button, the inline notice and the save call alike (`kmp-arch-v2` → blocking reasons).
- [ ] **Android + iOS screens** for the five steps: income; **monthly expense** (one typed figure, not an itemised list); debts (add/remove rows: name, balance, optional minimum payment and interest rate); investments (add/remove: name, amount); obligations (add/remove: name, monthly amount). A progress indicator throughout. **The first two steps carry no Skip control at all**; each of the last three does.
- [ ] **Save after every step** (`PUT`), so closing the app resumes where the user left off. Each save sends the whole wizard, including figures already entered. A failed save keeps the user's input and shows a retry — never loses typed figures.
- [ ] **Routing:** the wizard is the destination for the `financial_setup` onboarding step (2.5, Humble-Coders/Finance-backend#29) and cannot be escaped while it is outstanding. **Once it clears, go straight to home** — the optional steps are never re-offered, because nothing records whether they were declined; they are edited from the profile instead.
- [ ] All labels in `sharedLogic/i18n` (English); currency symbols and formatting from capabilities.
- [ ] Tests: `Money` edge cases; blocking reasons per step; repository decoding and error mapping on a mock engine; Android `UiState` derived rules.

## 🎯 Acceptance Criteria

- [ ] A user can complete every step. **The income and monthly-expense steps offer no Skip**, and the app cannot reach home until both are saved; the optional steps (debts, investments, obligations) can each be skipped, and the user still lands on home.
- [ ] Killing the app **before both figures are saved** and reopening resumes at the saved state, with the figures intact — the gate is still outstanding, so the wizard is still the destination.
- [ ] **Once both figures are saved the gate has cleared**, so a relaunch goes straight to home even if the user was part-way through an optional step. The optional steps are not offered again, whether they were filled or skipped; they are edited from the profile.
- [ ] Amounts are decimal strings from the text field to the wire; `util/Money` has tests for blanks, separators, too many decimals, huge values and zero; no `Double` in the diff.
- [ ] The Continue button, the inline message and the save path all read the same blocking-reason function.
- [ ] Validation and network errors show inline, in the design's style, and keep the user's input.
- [ ] Currency and formatting come from capabilities; nothing branches on country.
- [ ] Matches the approved design in light and dark mode, and meets the UI standards below.
- [ ] `./gradlew :androidApp:assembleDebug :sharedLogic:allTests` passes and the iOS `xcodebuild` succeeds (CI green on both jobs).
- [ ] No user-facing string literal in `androidApp` or `iosApp`.

## 🖼️ UI standards

*(From the team template, for Compose on Android and SwiftUI on iOS. Desktop is out of scope for this repo, so its lines are dropped.)*

### Design fidelity
- [ ] **Match the provided design exactly.** If a design is attached (screenshot / Figma / mockup), it is
      the source of truth — reproduce spacing, sizing, color, type, hierarchy, and every state faithfully.
      Do **not** approximate or silently "improve" it. *(Only when the ticket explicitly says "no design —
      build it yourself" do you design against the brand kit / design system.)*
- [ ] **The design is usually provided by the PM and is NOT attached to the issue.** At `/start-ticket`,
      **ask the PM for the design assets before building** — then build against those + the project's design
      system / brand kit.
- [ ] Use the **design-system tokens** (colors, type scale, spacing, radius, elevation) and
      **reuse/extend the shared components** — no one-off hardcoded colors/sizes, no duplicated component code.

### Theming
- [ ] Support **both light and dark themes.** Every color comes from a theme token defined in *both* modes;
      nothing hardcoded that breaks in the other. Verify the screen in light **and** dark.

### Native components
- [ ] Prefer **native platform components** wherever they achieve the design — top / nav bar, side bar /
      navigation drawer, tab bar, lists, dialogs, pickers, switches, menus, bottom sheets, etc. (Material on
      Android, HIG on iOS). Don't hand-roll what the platform already gives you.
- [ ] Where the design **cannot** be achieved with a native component, **tell the PM, explain the trade-off,
      and proceed** with the closest native approach or a minimal custom component — don't silently diverge.

### Layout, insets & responsiveness
- [ ] **Edge-to-edge, strictly.** The app draws to all screen edges — no default letterbox bars or
      system-colored chrome eating the layout. Backgrounds / gradients extend *under* the system bars.
- [ ] **Respect safe areas for content.** No content or interactive element sits under the **status bar,
      notch / display cutout, home indicator**, or — on Android — the **bottom gesture / navigation bar**
      (back / home). Apply the correct insets so content is never obscured or hard to tap; only decorative
      background bleeds underneath.
- [ ] **Responsive** across the supported device sizes (small phone → large phone → tablet / foldable where
      relevant) and **both orientations**. Use adaptive / constraint layouts, not fixed pixel positions; cap
      content width and center on large screens.
- [ ] **Correct text truncation** — overflowing text **ellipsizes (`…`)** cleanly on the intended number of
      lines instead of clipping, overlapping, or pushing the layout; wrap only where multi-line is intended.

### Input & keyboard
- [ ] **Right keyboard per field** — email keyboard for email, **numeric / number-pad for amounts,
      quantities, phone, OTP, PIN**, secure entry for passwords; set sensible autocapitalize / autocorrect /
      autofill hints (e.g. off for email & password, on for names).
- [ ] **Keyboard action buttons** — show the correct IME action (**Next** moves focus to the next field;
      **Done / Go / Search** submits or dismisses) and wire it up. Where the platform's keyboard lacks a
      return key (e.g. number pads), provide an on-keyboard **Done** via an accessory bar / toolbar.
- [ ] **Keep the focused field visible** — scroll / inset so the keyboard never covers the active field or
      its error message. Dismiss the keyboard on tap-outside / scroll where appropriate.

### States & feedback
- [ ] Define **loading, empty, error, and disabled** states for every screen that fetches or submits data.
      Disable controls and show progress during async work; surface errors inline (design-consistent), never
      as raw text dumps or silent failures.
- [ ] Consistent **press / hover / focus feedback** and transitions from the design system; keep motion
      subtle and **respect reduce-motion**.
- [ ] **Preserve UI state** across rotation / configuration change / process death —
      don't lose form input, scroll position, or selection.

### Accessibility & content
- [ ] Accessible labels / content descriptions on all interactive and informative elements; logical focus order.
- [ ] Respect **dynamic type / font scaling** — layouts don't break at the largest supported font size.
- [ ] Minimum touch-target size (~**48dp** Android / **44pt** iOS); sufficient color **contrast** (aim WCAG AA).
- [ ] **No hardcoded user-facing strings** — everything goes through the project's string / i18n resources.

### Architecture & verification
- [ ] Follow the project's UI architecture (`kmp-arch-v2`: native UI per platform, **no business logic in
      the UI**, ViewModels / state drive rendering). No secrets in the UI or committed.
- [ ] **Verify on the range:** smallest + largest supported device, **light + dark**, and
      the largest font scale — plus every state the design specifies.
