# [M3] Review and correct the extracted transactions

## 📖 Story / Why

Extraction is never perfect and, by design, there is no vision fallback to catch what it
misses — so every uncertain row lands here. This screen is where a pile of model output
becomes a ledger the user believes, and where they teach the categorizer: a correction
here is a rule for that household, so the same merchant lands right next month (PRD F3).

The tone matters. This is not an error list to be apologised for — it is the app asking
the user to confirm their own money. Twenty right rows and two wrong ones is the normal
case, so confirming everything must take one tap, and fixing the two must take two.

## 🧭 Context

- Repo: `FinAI-Mobile-2026`. No brief — drafted from `docs/ROADMAP.md` and the PRD.
- **Depends on 3.4** for the endpoints: `GET /transactions/review`,
  `PATCH /transactions/{id}`, confirm (single and bulk), delete, `POST /categories`.
- Reached from 3.6 after an import, and reachable on its own when rows are outstanding.
- Each row carries **why** it needs review — low confidence, unknown category, suspected
  duplicate. Show the reason; an undifferentiated list makes the user re-check rows that
  were fine.
- `kmp-arch-v2`: screen + ViewModel + UiState per platform; derived rules (what is
  outstanding, whether bulk confirm is available, what a correction will change) as
  computed values on the UiState so they can be unit-tested with plain constructors.
- Shared repository interface + Ktor implementation in `sharedLogic` first, following
  `KtorFinancialSetupRepository.kt` — `@Throws(ApiException::class,
  CancellationException::class)` on every public suspend fun.
- Money is decimal strings end to end via the shared `Money` util. Never a `Double`, never
  client-side cents.

## 🔑 Access & prerequisites

- Write access to `Humble-Coders/FinAI-Mobile-2026`; a Mac with Xcode for the iOS half.
- A backend with 3.3 and 3.4 deployed, or fakes, to exercise the states.

## ✅ Scope / What to build

- [ ] **Shared repository** for the review endpoints, with the model types and paging cursor
      in `sharedLogic/model/`.
- [ ] **The list**: date, description, amount, category, and the reason it needs review.
      Grouped by date. Amounts right-aligned and formatted through the shared formatter;
      debits and credits visually distinct without relying on colour alone.
- [ ] **Confirm all** — one action for the common case, with a clear count ("Confirm 18
      transactions"). Optimistic, with a rollback and a message if the request fails.
- [ ] **Correct a row** — category (a picker over the system taxonomy plus the household's
      own, with a way to create one), description, amount, date, direction. Number pad with
      a Done accessory for the amount.
- [ ] **Delete a row** that is not a transaction at all, with an undo window rather than a
      confirmation dialog — the common case is obvious junk, and a dialog per row is a tax
      on the normal path.
- [ ] **Suspected duplicates** shown next to what they matched, so the user can tell a real
      repeat purchase from a re-import. This is the one case where deleting the wrong row
      loses real data, so it gets the clearer treatment.
- [ ] **Say what a correction does.** When a category correction will also move other
      unreviewed rows for the same merchant, say so ("also applied to 3 others") — the
      backend returns the count. Silent bulk changes to someone's financial records are not
      acceptable, however convenient.
- [ ] **States**: loading, empty ("nothing needs review" — a good outcome, worded as one),
      error with retry, and a per-row saving state that does not block the rest of the list.
- [ ] Strings in `sharedLogic/i18n/`, including the category display names keyed by slug.

## 🎯 Acceptance Criteria

- [ ] The list renders every reason distinctly, and paging with the cursor neither skips nor
      repeats a row.
- [ ] Confirm-all clears the queue in one request, shows the count before acting, and rolls
      back visibly if the request fails.
- [ ] A category correction updates the row, reports how many others it also moved, and the
      screen reflects both without a manual refresh.
- [ ] Editing an amount uses the number pad, keeps the field visible above the keyboard, and
      round-trips the value exactly as a decimal string — a test asserts no `Double` in the
      path.
- [ ] Deleting offers undo, and undo restores the row.
- [ ] A suspected duplicate shows what it matched before the user can act on it.
- [ ] Rotation, configuration change and process death lose neither the in-progress edit nor
      the scroll position.
- [ ] Every derived rule is covered by UiState unit tests, not by inspecting the screen.
- [ ] **Android compiles and its tests pass, `:sharedLogic:testAndroidHostTest` passes, and
      the iOS workspace `xcodebuild` succeeds.**

## 🖼️ UI standards

**No design is provided for this screen** (manager decision, 2026-09-21) — build it against
what M2 established and the app's design tokens. That is a licence to design it, not a
licence to skip these.

- [ ] **Reuse what exists.** `ui/theme/` tokens on Android and `Brand` on iOS, `AppLoader` /
      `LoaderHost` for waits, `GradientButton`, the setup wizard's field styling
      (`AmountField` / `WizardField` in `ui/setup/SetupScreen.kt`, `SetupView.swift`). No
      one-off colours, no second loader, no duplicated field.
- [ ] **Light and dark.** Every colour from a token defined in both modes; verify in both.
- [ ] **Native components first** — Material on Android, HIG on iOS. Don't hand-roll a list,
      a sheet, a picker or a dialog the platform gives you. Where the design genuinely needs
      something custom, say so in the handoff rather than diverging silently.
- [ ] **Edge-to-edge, with correct insets.** Backgrounds bleed under the system bars; no
      content or tap target under the status bar, notch, home indicator or Android gesture
      bar.
- [ ] **Responsive** small phone → large phone → tablet, both orientations; cap content
      width and centre on large screens. Text ellipsizes cleanly rather than clipping or
      pushing the layout — merchant names are long and unpredictable.
- [ ] **Keyboard done properly** — number pad for amounts with a Done accessory (number pads
      have no return key), Next/Done actions wired, the focused field never hidden behind
      the keyboard.
- [ ] **Loading, empty, error and disabled states** for everything that fetches or submits.
      Errors inline and localized, never a raw message dumped on screen.
- [ ] **State survives** rotation, configuration change and process death — nothing typed is
      lost.
- [ ] **Accessibility**: labels on every interactive element, logical focus order, 48dp /
      44pt targets, layouts that hold at the largest font scale, AA contrast.
- [ ] **No hardcoded strings** — everything through `sharedLogic/i18n/`.
- [ ] **Verify on the range**: smallest and largest supported device, light and dark, largest
      font scale, and every state.
