# [M2] Build the splash screen and signup flow

## 📖 Story / Why

This is the first thing every user sees, and the first real screens in the app. The target is **signup in about 30 seconds** (PRD F1).

The app opens on a **splash screen** that stays up exactly as long as it takes to decide where the user goes — restoring the saved session and asking the API what is still outstanding. A returning user should never see the signup screen flash before home.

Three routes, and **every one ends with a verified phone number** (PRD §4.6):
1. **Phone + country code → 6-digit SMS code** — the primary route.
2. **Continue with Google → phone → code.**
3. **Continue with Apple → phone → code** (iOS). Sign in with Apple is mandatory on iOS whenever Google is offered (App Store guideline 4.8).

The phone step after Google/Apple is not optional. The verified number is the **identity key** that stops one person becoming two households (Apple's *Hide My Email* makes email useless for that), and it is where the **region** comes from (2.1). After the phone come the steps the API asks for — region, consent — then the financial setup wizard (2.4), then home.

Two rules from the PRD shape the UX: **signup is never hard-blocked on region**, and **the region override is reachable during onboarding** — a misdetected Canadian can fix it on the spot.

## 🧭 Context

- Repo: `FinAI-Mobile-2026`. Native UI — Compose on Android, SwiftUI on iOS — over `sharedLogic` (`kmp-arch-v2`).
- **No brief.** M2 is drafted from `docs/ROADMAP.md` (2.3) and the PRD, which are the yardstick for review (manager decision, 2026-09-11).
- **What exists (#6):** `SupabaseAuthRepository` (phone OTP request/verify, sign-out, `sessionState` as a `Flow`), `SupabaseTokenSource`, the Render API client with typed `ApiException`, `KtorCapabilitiesRepository`, `Me` with `onboardingRequired`, the strings registry, a theme stub (`ui/theme/Theme.kt`). **No navigation exists** — `MainActivity` and `iOSApp.swift` show the ticket-6 demo.
- **How the app launches today:** Android's manifest uses the platform theme `@android:style/Theme.Material.Light.NoActionBar` — light only, so the system splash every app gets on Android 12+ is a **white screen even in dark mode** — and there is no `androidx.core:core-splashscreen` dependency. iOS generates a **blank** launch screen (`INFOPLIST_KEY_UILaunchScreen_Generation = YES`), and the asset catalog holds only the app icon and accent colour. `SessionState` starts at `LOADING` while the saved session restores (#6). The first `/me` can be slow: Render's free tier can take most of a minute to wake, and `FinAiHttpClient` allows 60 seconds.
- **Supabase calls (supabase-kt 3.7.0, checked):** sign in with a provider token — `auth.signInWith(IDToken) { idToken = …; provider = Google | Apple; nonce = … }`; add a phone to a signed-in user — `auth.updateUser { phone = … }`, then `auth.verifyPhoneOtp(OtpType.Phone.PHONE_CHANGE, phone, code)`.
- **Provider SDKs are per platform** (`kmp-arch-v2`: native SDK → per-platform code; the ID token then goes through the shared repository):
  - Android Google — Credential Manager (`androidx.credentials` + Google's ID library).
  - iOS Apple — AuthenticationServices. Generate a random nonce; send its SHA-256 to Apple and the raw value to Supabase.
  - iOS Google — the Google Sign-In SDK (the app already uses CocoaPods). If the SDK cannot supply a nonce, the Supabase Google provider needs "skip nonce check" — a dashboard setting the manager owns.
- **Apple on iOS only** (manager-confirmed, 2026-09-11). Android offers phone + Google. Someone who signed up with Apple on an iPhone signs in on Android with their phone number and lands in the same account — the phone is the identity key.
- **The onboarding contract is 2.1's:** `/me` returns `onboarding_required` — `phone`, `region`, `consent` — and the app routes on it. It never infers a step itself. Unknown values already decode to `OnboardingStep.UNKNOWN` (#6), which must count as "not done".
- **Phone already taken:** the API answers `409 {"detail":{"code":"phone_already_linked"}}` (`Finance-backend` `app/api/deps.py:40-50`). The app maps any 409 to a generic `Validation` today (`ApiErrorMapper.kt`), so this ticket adds a typed error. **Supabase may refuse a number already held by another sign-in before the API ever sees it — verify what it returns at the start of the ticket**, and map both to the same typed error. The message is: *"This number already has an account — sign in with your phone number instead."* Merging two sign-in methods into one account is a follow-up (manager-confirmed, 2026-09-11).
- **Country code pre-selection** from the device region and time zone is a UX nicety only (PRD §4.6) — nothing downstream depends on it. The dial-code list is shared data, not per-country code.
- **Carry-over from M1** (`docs/ROADMAP.md`): remove the ticket-6 demo — `ApiDemoScreen` / `ApiDemoViewModel` / `ApiDemoUiState` (Android), `ApiDemoView` / `ApiDemoViewModel` (iOS), the demo aids `expireAccessTokenForTesting` and `tokenSecondsLeftForTesting` on `SupabaseAuthRepository`, and the unused `ContentView.swift` and `PlaceholderScreen.kt`. iOS view models must **store their `Task`s and cancel them on unbind** — the demo does not, and must not be copied.

- **Design: the PM provides the approved design; it is not attached to this issue.** At `/start-ticket`, ask the PM for it before building. The bar is to **match it exactly** — spacing, sizing, colour, type and every state — not to approximate or improve it (manager decision, 2026-09-11).

## ✅ Scope / What to build

**Shared (`sharedLogic`)**
- [ ] `AuthRepository`: `signInWithIdToken(provider, idToken, nonce)`, `requestPhoneLink(phone)` and `verifyPhoneLink(phone, code)` (`updateUser` + `PHONE_CHANGE`) — all `@Throws(ApiException::class, CancellationException::class)`.
- [ ] Remove the two demo aids from `SupabaseAuthRepository`.
- [ ] `ApiException.PhoneAlreadyLinked`, mapped from the API's `phone_already_linked` code and from Supabase's equivalent error.
- [ ] `OnboardingStep.REGION` and `OnboardingStep.CONSENT`; the `Me` fields 2.1 adds.
- [ ] `PUT /me/region` and `POST /me/consent` in the shared Ktor layer.
- [ ] **One routing function** — session state + `/me` + setup status → the next screen (splash, signup, phone, code, region, consent, wizard, home) — pure and unit-tested as a matrix. Both platforms read it; neither decides on its own.
- [ ] The dial-code list and a default-country function (device region, then time zone), tested.
- [ ] All strings in `i18n` (English).

**Android**
- [ ] `navigation/`: a `Route` enum and a state-variable router (`kmp-arch-v2` → Navigation); `MainActivity` starts it.
- [ ] Screens: welcome (phone entry with country picker, Continue with Google), code entry (six digits, resend with the 60-second countdown), the phone step after Google, region (the detected region, with a way to change it — no confirmation screen), consent (2.1's draft terms), and a placeholder home with Sign out.
- [ ] Google via Credential Manager.

**iOS**
- [ ] A root router; `iOSApp.swift` starts it.
- [ ] The same screens in SwiftUI, plus **Continue with Apple**; Google via the Google Sign-In SDK.
- [ ] View models store their `Task`s and cancel them on unbind.

**Splash (both platforms)**
- [ ] The routing function's first state is **Splash** while the session is `LOADING` or the first `/me` (and setup status) is in flight; it then hands off to signup, the next onboarding step, or home.
- [ ] **Android:** add `androidx.core:core-splashscreen`; give the launch activity a splash theme (icon and background colour, light and dark) in place of the light-only platform theme; call `installSplashScreen()` in `MainActivity` with `setKeepOnScreenCondition` tied to the Splash state.
- [ ] **iOS:** replace the generated blank launch screen with one showing the logo on the background colour from the asset catalog (light and dark variants), and a matching SwiftUI splash view for the router's Splash state, so the hand-off is seamless.
- [ ] **No artificial delay** — the splash lasts as long as the work, never a fixed timer.
- [ ] **Never stuck:** if the first `/me` is slow, show a progress indicator after a few seconds rather than a frozen logo; if it fails, move to an error screen with Retry. An unconfigured build shows the existing configuration message (#6).

**Both**
- [ ] A signed-in user with nothing outstanding goes from the splash straight to home on launch.
- [ ] Errors: wrong or expired code, the resend limit, no network, phone already taken (the message above), provider sheet cancelled (silently back, no error).
- [ ] Delete the demo files and the unused placeholders (carry-over above).

## 🎯 Acceptance Criteria

- [ ] **Phone route**, on Android and iOS: number → code → (region/consent as required) → home, and the API's `/me` shows the phone and a region.
- [ ] **Google route**, on Android and iOS, and **Apple route** on iOS: provider → phone → code → home. **No path reaches home without a verified phone.**
- [ ] The household's region is shown during onboarding and can be changed there; a number the API cannot place requires picking a region.
- [ ] Consent is recorded before home, and the app never reaches home while `onboarding_required` is non-empty.
- [ ] **Cold start**, on both platforms: a signed-out user sees the splash, then welcome; a signed-in, fully onboarded user sees the splash, then home — **with no flash of welcome in between**. Sign out returns to welcome.
- [ ] The splash lasts only while the session restores and the first `/me` loads — no fixed delay. A slow API shows progress; no network gives way to an error with Retry.
- [ ] The launch screen and splash match the design in light and dark mode — **no white flash in dark mode on Android**.
- [ ] Using the second test number from another account shows the phone-already-taken message and creates no second household (checked through `/me` on both sessions).
- [ ] The routing function has a test for every combination of session state and `onboarding_required` value, including `UNKNOWN`.
- [ ] The demo screens, demo aids, `ContentView.swift` and `PlaceholderScreen.kt` are gone.
- [ ] `ThrowsAnnotationGuardTest` passes; no user-facing string literal in `androidApp` or `iosApp`.
- [ ] Matches the approved design in light and dark mode, and meets the UI standards below.
- [ ] `./gradlew :androidApp:assembleDebug :sharedLogic:allTests` passes and the iOS `xcodebuild` succeeds (CI green on both jobs).

## 🖼️ UI standards

*(From the team template, for Compose on Android and SwiftUI on iOS. Desktop is out of scope for this repo, so its lines are dropped.)*

### Design fidelity
- [ ] **Match the provided design exactly.** If a design is attached (screenshot / Figma / mockup), it is
      the source of truth — reproduce spacing, sizing, color, type, hierarchy, and every state faithfully.
      Do **not** approximate or silently "improve" it. *(Only when the ticket explicitly says "no design —
      build it yourself" do you design against the brand kit / design system.)*
- [ ] **The design is usually provided by the PM and is NOT attached to the issue.** At `/start-ticket`,
      **ask the PM for the design assets before building** — then build against those + the project's design
      system / brand kit.
- [ ] Use the **design-system tokens** (colors, type scale, spacing, radius, elevation) and
      **reuse/extend the shared components** — no one-off hardcoded colors/sizes, no duplicated component code.

### Theming
- [ ] Support **both light and dark themes.** Every color comes from a theme token defined in *both* modes;
      nothing hardcoded that breaks in the other. Verify the screen in light **and** dark.

### Native components
- [ ] Prefer **native platform components** wherever they achieve the design — top / nav bar, side bar /
      navigation drawer, tab bar, lists, dialogs, pickers, switches, menus, bottom sheets, etc. (Material on
      Android, HIG on iOS). Don't hand-roll what the platform already gives you.
- [ ] Where the design **cannot** be achieved with a native component, **tell the PM, explain the trade-off,
      and proceed** with the closest native approach or a minimal custom component — don't silently diverge.

### Layout, insets & responsiveness
- [ ] **Edge-to-edge, strictly.** The app draws to all screen edges — no default letterbox bars or
      system-colored chrome eating the layout. Backgrounds / gradients extend *under* the system bars.
- [ ] **Respect safe areas for content.** No content or interactive element sits under the **status bar,
      notch / display cutout, home indicator**, or — on Android — the **bottom gesture / navigation bar**
      (back / home). Apply the correct insets so content is never obscured or hard to tap; only decorative
      background bleeds underneath.
- [ ] **Responsive** across the supported device sizes (small phone → large phone → tablet / foldable where
      relevant) and **both orientations**. Use adaptive / constraint layouts, not fixed pixel positions; cap
      content width and center on large screens.
- [ ] **Correct text truncation** — overflowing text **ellipsizes (`…`)** cleanly on the intended number of
      lines instead of clipping, overlapping, or pushing the layout; wrap only where multi-line is intended.

### Input & keyboard
- [ ] **Right keyboard per field** — email keyboard for email, **numeric / number-pad for amounts,
      quantities, phone, OTP, PIN**, secure entry for passwords; set sensible autocapitalize / autocorrect /
      autofill hints (e.g. off for email & password, on for names).
- [ ] **Keyboard action buttons** — show the correct IME action (**Next** moves focus to the next field;
      **Done / Go / Search** submits or dismisses) and wire it up. Where the platform's keyboard lacks a
      return key (e.g. number pads), provide an on-keyboard **Done** via an accessory bar / toolbar.
- [ ] **Keep the focused field visible** — scroll / inset so the keyboard never covers the active field or
      its error message. Dismiss the keyboard on tap-outside / scroll where appropriate.

### States & feedback
- [ ] Define **loading, empty, error, and disabled** states for every screen that fetches or submits data.
      Disable controls and show progress during async work; surface errors inline (design-consistent), never
      as raw text dumps or silent failures.
- [ ] Consistent **press / hover / focus feedback** and transitions from the design system; keep motion
      subtle and **respect reduce-motion**.
- [ ] **Preserve UI state** across rotation / configuration change / process death —
      don't lose form input, scroll position, or selection.

### Accessibility & content
- [ ] Accessible labels / content descriptions on all interactive and informative elements; logical focus order.
- [ ] Respect **dynamic type / font scaling** — layouts don't break at the largest supported font size.
- [ ] Minimum touch-target size (~**48dp** Android / **44pt** iOS); sufficient color **contrast** (aim WCAG AA).
- [ ] **No hardcoded user-facing strings** — everything goes through the project's string / i18n resources.

### Architecture & verification
- [ ] Follow the project's UI architecture (`kmp-arch-v2`: native UI per platform, **no business logic in
      the UI**, ViewModels / state drive rendering). No secrets in the UI or committed.
- [ ] **Verify on the range:** smallest + largest supported device, **light + dark**, and
      the largest font scale — plus every state the design specifies.
