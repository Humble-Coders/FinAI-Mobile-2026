# [M3] Add a transaction by hand

## 📖 Story / Why

Since the vision fallback was deliberately removed (PRD §9, 2026-09-21), **typing a
transaction in is the only way in when a document cannot be read** — a blurred photo, an
unusual layout, a bank we have not tuned for. Without this screen those users are simply
stuck, and the import flow has nothing to offer them.

It is also the low-commitment way to try the product: three transactions typed in, before
trusting it with a bank statement.

## 🧭 Context

- Repo: `FinAI-Mobile-2026`. No brief — drafted from `docs/ROADMAP.md` and the PRD.
- Backend counterpart: the manual-entry ticket in `Finance-backend` (`POST /transactions`).
- Reachable from the home screen **and** from 3.6's "nothing could be read" state — that
  second entry point is the whole reason this ticket exists in M3.
- `kmp-arch-v2`: screen + ViewModel + UiState; validation rules as computed values on the
  UiState, mirroring the blocking-reason pattern the setup wizard already uses
  (`SetupWizard.blockingReason`) rather than a second validation style.
- Money is decimal strings end to end through the shared `Money` util.

## 🔑 Access & prerequisites

- Write access to `Humble-Coders/FinAI-Mobile-2026`; a Mac with Xcode for the iOS half.
- The backend endpoint deployed, or a fake.

## ✅ Scope / What to build

- [ ] **Shared repository** method for `POST /transactions`, with the request model in
      `sharedLogic/model/`.
- [ ] **The form**: account (from 3.3's list, with inline create), date (defaulting to
      today, never in the future), amount, direction (money out / money in — worded in
      plain language, not "debit/credit"), description, optional category.
- [ ] **Blocking reasons, shared.** One function returning a typed reason-or-null that the
      disabled Save button, the inline notice and the submit path all read — the same
      pattern as the setup wizard, so a greyed-out button and a server refusal can never
      disagree.
- [ ] **The duplicate answer.** The backend returns 409 when the entry matches an existing
      transaction; show what it matched and let the user keep it anyway or cancel. Do not
      swallow it, and do not show a generic error — "you already have this" is useful
      information.
- [ ] **Leave the category alone when the user sets one.** If they do not, the backend
      categorizes; the screen says so rather than showing an empty category silently.
- [ ] Strings in `sharedLogic/i18n/`.

## 🎯 Acceptance Criteria

- [ ] A transaction typed in saves and appears with `source = manual`; the amount
      round-trips exactly as a decimal string, with no `Double` in the path.
- [ ] Save is disabled until the form is valid, and the reason is shown inline — covered by
      UiState unit tests with plain constructors.
- [ ] The amount field uses the number pad with a Done accessory and stays visible above the
      keyboard.
- [ ] A future date is refused before the request is made.
- [ ] A duplicate returns 409 and the screen shows what it matched, with both ways out.
- [ ] Reachable from 3.6's unreadable-document state, and that path is exercised by a test.
- [ ] Rotation and process death do not lose what was typed.
- [ ] **Android compiles and its tests pass, `:sharedLogic:testAndroidHostTest` passes, and
      the iOS workspace `xcodebuild` succeeds.**

## 🚫 Out of scope

- The endpoint — the backend ticket of the same number.
- Editing an existing transaction — **3.7** already does that.
- Recurring transactions, splits, CSV import — not in v1.

## 🔗 Dependencies

- Needs the backend manual-entry ticket, and 3.3 beneath it for accounts and categories.
- 3.6 links to this from its empty state.

## 🖼️ UI standards

**No design is provided for this screen** (manager decision, 2026-09-21) — build it against
what M2 established and the app's design tokens. That is a licence to design it, not a
licence to skip these.

- [ ] **Reuse what exists.** `ui/theme/` tokens on Android and `Brand` on iOS, `AppLoader` /
      `LoaderHost` for waits, `GradientButton`, the setup wizard's field styling
      (`AmountField` / `WizardField` in `ui/setup/SetupScreen.kt`, `SetupView.swift`). No
      one-off colours, no second loader, no duplicated field.
- [ ] **Light and dark.** Every colour from a token defined in both modes; verify in both.
- [ ] **Native components first** — Material on Android, HIG on iOS. Don't hand-roll a list,
      a sheet, a picker or a dialog the platform gives you. Where the design genuinely needs
      something custom, say so in the handoff rather than diverging silently.
- [ ] **Edge-to-edge, with correct insets.** Backgrounds bleed under the system bars; no
      content or tap target under the status bar, notch, home indicator or Android gesture
      bar.
- [ ] **Responsive** small phone → large phone → tablet, both orientations; cap content
      width and centre on large screens. Text ellipsizes cleanly rather than clipping or
      pushing the layout — merchant names are long and unpredictable.
- [ ] **Keyboard done properly** — number pad for amounts with a Done accessory (number pads
      have no return key), Next/Done actions wired, the focused field never hidden behind
      the keyboard.
- [ ] **Loading, empty, error and disabled states** for everything that fetches or submits.
      Errors inline and localized, never a raw message dumped on screen.
- [ ] **State survives** rotation, configuration change and process death — nothing typed is
      lost.
- [ ] **Accessibility**: labels on every interactive element, logical focus order, 48dp /
      44pt targets, layouts that hold at the largest font scale, AA contrast.
- [ ] **No hardcoded strings** — everything through `sharedLogic/i18n/`.
- [ ] **Verify on the range**: smallest and largest supported device, light and dark, largest
      font scale, and every state.
